**第二轮中发现并修复的缺陷**(全部有回归测试或复验):
1. 规则抽屉表单被匹配面板 `replaceChildren` 清空 → 改为追加包装节点(复验:表单齐全=true)。
2. "暂停中"误报(停用账号被推断为过渡态)→ 改为 applyControl 显式标记集合。
3. 金额列"—"(列表契约为嵌套 `amount.minor_units`)→ 修正概览与订单两处解析。
4. 待处理动作缺失(契约为 `category/reason` 且 `allowed_actions` 已是数组)→ 修正解析(复验:补发/终止呈现)。
5. (并行会话遗留)`build_runtime` 在 Tokio 上下文外 spawn 导致 serve 启动 panic → 移入 `rt.block_on` 构造。

**已知限制/备注**:
- 概览「手动刷新」在停服时错误被轮询器静默吞掉(poll.ts `catch(() => undefined)`),页面级错误块仅在首次加载/路由进入时出现——符合"页面刷新或重开仍存在"底线,但手动刷新无失败提示可后续增强。
- 人工动作(补发/终止等)的服务端成功路径依赖完整执行守卫与真实协议管道;mock 种子无守卫行时服务端拒绝并如实报错(界面正确呈现)。实单成功路径归入 001 的 SC-091 实账号验证范围。
- 规则编辑为"整体替换"语义:001 契约无读取既有正文的端点,抽屉以显著警告明示(US4 冲突警告)。
- 30 秒自动刷新的"无布局跳变"以固定统计卡节点原地更新实现并走查确认;帧级布局稳定性未做自动化断言。
- IAB 标签页在服务进程被杀瞬间曾出现一次渲染器崩溃(环境行为,恢复后正常),应用层无崩溃。
- 扫码接入弹窗的完整状态机(轮询/过期重取)有单测覆盖;mock 无 QR 驱动,浏览器内仅能走到"创建二维码会话"步骤,完整扫码授权待 live 实账号(SC-091)。
