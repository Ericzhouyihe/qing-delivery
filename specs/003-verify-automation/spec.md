# Feature Specification: 安全验证自动化(003-verify-automation)

**Feature Branch**: `003-verify-automation`

**Created**: 2026-09-23

**Status**: Draft

**Input**: User description: "官方安全验证(滑块风控)自动化处理——浏览器自动化子系统 T050/T051,触发检测→浏览器拉起→滑块处理→Cookie 回写→失败转人工,参考 Ydisks-Xianyu-Helper internal/browser 但按宪章重新实现验证"。背景:实账号扫码接入已通(002 收敛后首次实机验证),账号长期在线必然遇到平台安全验证/滑块风控;当前系统仅"指引转人工",原项目该能力为一整套浏览器自动化子系统。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 风控自动处置 (Priority: P1)

卖家账号在线值守期间,平台因风控要求安全验证(token 刷新风控/滑块/官方安全验证)。系统自动检测到验证信号 → 自动拉起受控浏览器打开验证页 → 自动完成滑块验证 → 读取验证后的新凭证并加密保存、热更新账号会话 → 账号恢复在线。全程无需卖家干预;管理页实时显示处置进度(检测到验证 → 浏览器已打开 → 滑块处理中 → 凭证已更新/恢复在线)。

**Why this priority**: 安全验证是长时值守的必然事件(原项目经验:token 刷新触发风控是高频场景);不能自动通过则账号掉线、自动交付中断,这是"无人值守"承诺的成败点。

**Independent Test**: 用已授权真实账号触发一次平台验证(或手动触发入口走同流程),观察自动处置进度与账号恢复。

**Acceptance Scenarios**:

1. **Given** 账号在线值守, **When** 平台返回要求安全验证的信号, **Then** 系统在 10 秒内识别并开始自动处置,界面出现该账号的"验证中"状态与分步进度。
2. **Given** 自动处置进行中, **When** 滑块在浏览器中完成且平台确认通过, **Then** 新凭证被加密保存、账号会话热更新,账号状态在 2 分钟内回到在线,处置记录标记成功及耗时。
3. **Given** 验证处置进行中, **When** 该账号收到新的付款事件, **Then** 该账号的交付动作被暂停排队(不使用可能失效的凭证发货),验证完成后按原不变量继续处理;其他账号不受影响。
4. **Given** 自动处置成功, **When** 卖家稍后打开管理页, **Then** 可在账号详情看到这次验证的完整记录(触发原因/方式=自动/结果/耗时/凭证已更新)。

---

### User Story 2 - 失败降级转人工 (Priority: P1)

自动处置失败(滑块多次未通过、验证页超时、浏览器环境不可用等)时,系统不无限重试:达到重试上限(默认 2 次)或超时(默认 120 秒)后停止,生成"安全验证"类待处理事项,内含**一键打开验证页**的入口与失败原因;卖家人工完成验证后,系统自动检测到凭证恢复并关闭事项、恢复账号。原始失败原因完整保留可追溯;降级后不再自动紧密重试(重试间隔分钟级起)。

**Why this priority**: 自动滑块不可能 100% 通过;可靠的降级路径保证"最坏情况也只是点一下链接",不让账号处于无人知晓的挂死状态。

**Independent Test**: 构造处置失败(如断网/遮挡滑块),观察待处理事项生成、手动链接可开、人工完成后事项自动关闭。

**Acceptance Scenarios**:

1. **Given** 自动处置连续失败达到重试上限, **When** 系统停止自动尝试, **Then** 生成"安全验证"待处理事项(含失败原因与打开验证页按钮),账号卡显示"待人工验证",且至少 5 分钟内不再次自动拉起浏览器。
2. **Given** 待处理事项存在, **When** 卖家点击事项中的验证入口并完成人工验证, **Then** 系统在 60 秒内检测到凭证恢复,自动关闭事项、账号恢复在线,全过程无需重启服务。
3. **Given** 降级转人工后, **When** 卖家查看该账号详情, **Then** 可看到每次自动尝试的记录(尝试次数、每次失败原因),无信息丢失。
4. **Given** 本机缺少可用浏览器组件, **When** 验证被触发, **Then** 系统明确提示"浏览器不可用+安装指引"并直接转人工,不伪称已尝试(宪章:不虚报)。

---

### User Story 3 - 浏览器生命周期管理 (Priority: P2)

受控浏览器实例有明确的生命周期策略:按需创建、同账号复用、空闲回收(默认 5 分钟无任务即关闭)、服务退出时全部清理;并发上限(默认同时 1 个实例)防止资源失控;实例崩溃可自动重建。管理页设置区可见浏览器策略与当前运行状态。

**Why this priority**: 浏览器是重量级资源(数百 MB 内存);无生命周期治理的自动化会拖垮常驻服务。宪章 III 明确要求创建/复用/回收/退出策略。

**Independent Test**: 触发一次验证后观察:处置结束浏览器在空闲时限内关闭、任务管理器无残留进程;服务停止后无任何浏览器残留。

**Acceptance Scenarios**:

1. **Given** 一次验证处置完成, **When** 空闲超过时限, **Then** 浏览器实例自动关闭,无残留进程。
2. **Given** 两个账号几乎同时触发验证, **When** 并发上限为 1, **Then** 第二个排队等待(界面显示排队),不并发拉起两个浏览器。
3. **Given** 服务正常退出, **When** 退出完成, **Then** 全部受控浏览器进程被清理(系统进程列表无残留)。
4. **Given** 浏览器实例异常崩溃, **When** 验证仍在进行, **Then** 系统按重试策略重建实例继续或降级转人工,不挂死。

---

### User Story 4 - 手动触发验证 (Priority: P2)

卖家可在账号页主动发起安全验证(升级 002 的"查看验证"入口:从仅指引变为可实际完成验证的同一流程);场景:卖家预感风控、或按平台提示提前验证。

**Why this priority**: 复用同一处置管道的低成本增强,给卖家主动控制权。

**Independent Test**: 账号页点击"发起验证",走完整处置流程并看到结果。

**Acceptance Scenarios**:

1. **Given** 账号已接入, **When** 卖家点击"发起验证", **Then** 走与自动触发完全相同的处置流程与进度呈现,审计记录方式=手动。
2. **Given** 手动验证进行中, **When** 卖家关闭管理页, **Then** 验证流程继续在后台完成(不依赖页面打开)。

---

### User Story 5 - 验证审计与状态呈现 (Priority: P2)

每次验证尝试产生审计记录(触发原因、方式自动/手动、开始/结束时间、结果、耗时、凭证是否更新、失败原因),按账号关联;账号卡新增验证状态徽章(正常/验证中/待人工);待处理工作台新增"安全验证"分组。

**Why this priority**: 可追溯性(宪章 IV)与卖家对自动化行为的可见性。

**Independent Test**: 触发自动+手动各一次验证,检查审计记录字段完整、分组与徽章正确。

**Acceptance Scenarios**:

1. **Given** 发生过一次自动成功与一次自动失败转人工, **When** 打开账号详情, **Then** 两条记录齐全且字段完整(原因/方式/结果/耗时/凭证更新结果)。
2. **Given** 存在待人工验证事项, **When** 打开待处理工作台, **Then** "安全验证"分组出现且计数正确,侧边栏角标联动。

---

### Edge Cases

- 滑块反复不通过:达到上限即转人工,绝不紧密重试(重试间隔 ≥1 分钟)。
- 验证页加载超时/网络中断:按超时处理转人工或按策略重试一次。
- 滑块通过但凭证保存失败:保留旧凭证不损坏现有会话,记录"凭证更新失败"并转人工。
- 误报防护:仅明确的验证信号触发浏览器拉起;普通消息/心跳不得触发(48 小时常驻 0 误拉起)。
- 验证期间服务被要求停止:等待在途处置收尾(有上限)后随服务退出,不留孤儿浏览器进程。
- 用户数据目录损坏或被其他程序锁定:如实报错转人工,不删除重建用户数据目录。
- 多账号风控风暴:并发上限排队;队列超时的事项转人工。
- 与交付不变量的关系:验证流程绝不改变 unknown 不自动重发、guard 互斥、重试预算等语义;验证中暂停的交付在恢复后按原状态机继续。
- 界面关闭不影响处置(后台值守完成);界面仅呈现进度与结果。

## Requirements *(mandatory)*

### Functional Requirements

**触发与处置**

- **FR-001**: 系统 MUST 在账号值守期间识别平台安全验证信号(至少覆盖实账号观察到的 token 风控/滑块类信号),并在 10 秒内开始自动处置;仅明确信号可触发,普通消息不得触发浏览器拉起。
- **FR-002**: 自动处置 MUST 完成:拉起受控浏览器 → 打开验证页 → 自动完成滑块 → 读取验证后凭证 → 加密保存并热更新账号会话;各步骤进度在管理页实时可见。
- **FR-003**: 验证处置期间,该账号 MUST 暂停新的交付触发(不使用可能失效的凭证),验证完成后恢复并按原状态机继续;其他账号的值守与交付不受影响。
- **FR-004**: 自动处置 MUST 有重试上限(默认 2 次)与总超时(默认 120 秒);超限后停止并转人工,降级后自动重试间隔 MUST ≥5 分钟。
- **FR-005**: 转人工 MUST 生成"安全验证"类待处理事项,含失败原因与一键打开验证页入口;人工完成后系统 MUST 在 60 秒内自动检测凭证恢复、关闭事项并恢复账号。
- **FR-006**: 卖家 MUST 可在账号页手动发起安全验证,走同一处置管道;审计记录方式为手动;处置不依赖管理页保持打开。

**浏览器资源**

- **FR-007**: 受控浏览器 MUST 具备生命周期策略:按需创建、同账号复用、空闲回收(默认 5 分钟)、服务退出全量清理;并发实例上限默认 1,超出的验证请求排队且队列有时限。
- **FR-008**: 浏览器组件不可用时,系统 MUST 明确报告"浏览器不可用"+安装指引,并直接转人工;不得伪称已尝试或已成功(宪章:不虚报能力)。
- **FR-009**: 验证处置 MUST 全程在本机完成;系统 MUST NOT 默认使用任何第三方远程验证/打码服务;如未来引入须显式配置开关并说明数据流向。

**呈现与审计**

- **FR-010**: 每次验证尝试 MUST 产生审计记录:触发原因、方式(自动/手动)、起止时间、结果、耗时、凭证是否更新、失败原因;按账号关联且界面可查。
- **FR-011**: 账号卡 MUST 呈现验证状态徽章(正常/验证中/待人工);待处理工作台 MUST 新增"安全验证"分组并联动侧边栏角标。
- **FR-012**: 能力声明接口 MUST 暴露浏览器可用性状态,界面如实展示(延续 002 FR-011)。

**安全与不变量**

- **FR-013**: 验证流程 MUST NOT 改变 001 交付安全不变量(unknown 不自动重发、guard 互斥、重试预算、人工操作确认流);验证相关人工动作同样走统一确认流。
- **FR-014**: 凭证更新 MUST 复用现有加密存储(不新增明文落盘);更新失败时保留旧凭证,不得损坏现有会话。

### Key Entities *(include if feature involves data)*

- **验证会话(VerificationSession)**: 一次验证处置的聚合。状态机:`detected → browser_open → solving → updating_credential → succeeded | failed_manual`;携带账号、触发原因(自动信号来源/手动)、重试计数、时限。
- **浏览器实例策略(BrowserInstancePolicy)**: 并发上限、空闲回收时限、队列时限;及当前运行状态(空闲/处置中/排队数)。
- **验证审计记录(VerificationAuditEntry)**: 账号、原因、方式、起止、结果、耗时、凭证更新结果;只增不改。
- **安全验证事项(SecurityVerificationIssue)**: 待处理工作台的新类别;关联验证会话;关闭方式=凭证恢复检测或人工关闭(带原因)。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-301**: 实账号端到端:真实触发安全验证时,自动处置完成且账号在 5 分钟内恢复在线、无需人工(实账号验证项,纳入 R-矩阵)。
- **SC-302**: 失败降级 100% 可靠:所有构造的失败路径(滑块不过/超时/无浏览器)均生成含可点击验证入口的待处理事项,且 5 分钟内无第二次自动拉起。
- **SC-303**: 进程卫生:处置结束空闲时限后与服务正常退出后,系统进程列表中受控浏览器残留数为 0。
- **SC-304**: 误报为零:正常在线常驻 48 小时,非验证信号导致的浏览器拉起次数为 0。
- **SC-305**: 审计完整:抽任意一次尝试,审计字段(原因/方式/起止/结果/耗时/凭证更新)100% 可查;凭证更新失败场景旧凭证完好、原会话可继续。
- **SC-306**: 回归基线:现有测试(前端 80 + Rust 131)全部保持通过;交付安全不变量相关测试零修改通过。
- **SC-307**: 资源预算:处置中浏览器峰值内存 ≤500MB;空闲回收在时限内完成;单次处置总时长(不含人工)≤3 分钟。

## Assumptions

- 触发信号集合以实账号观察为准,首版覆盖 token 风控/滑块类信号;新信号类型按需补充并记录(不虚报覆盖面)。
- 默认以**可见浏览器窗口**(有头模式)执行滑块——通过率优先,卖家可旁观;无头模式作为可选配置。此为默认决策,计划阶段可依据实测调整。
- 本机需有可用 Chromium 系浏览器;缺失时给出安装指引。不打包浏览器进发行包(安装体积),计划阶段论证。
- 参考 Ydisks-Xianyu-Helper 的**流程与策略**(生命周期/降级链/审计思想),Rust 侧为新实现并重新验证;如移植实质代码须先核对其许可证义务(宪章 V)。不照搬其远程打码/密码登录/浏览器补订单等超出本范围的能力。
- 001 的 T050/T051(官方验证浏览器流程/CDP 管理器)由本规格承接实现并在 001 清单中关闭,不再双处跟踪。
- 范围不含:密码登录、二维码续期(已有真实扫码通道)、浏览器补抓订单(订单以协议为主,浏览器补足另行立项)。
- 单管理员本地场景不变;验证处置在核心服务后台完成,不依赖管理页打开。
