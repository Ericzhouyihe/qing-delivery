# 轻交付（qing-delivery）Constitution

## Core Principles

### I. 以已付款订单和可恢复交付为核心

轻交付面向虚拟商品卖家，核心职责是把正确的链接、说明或卡密交付给正确订单的买家。
发货必须由平台可信交易事件或经核验的订单事实触发；聊天关键词或 AI 推断不能证明付款。

- 发货前必须核对平台、账号、卖家身份、订单、买家、商品、规格、数量和可发货状态。
  必要事实缺失或矛盾时必须等待补全或转人工处理，不得猜测身份、规格或付款状态。
- 闲鱼优先消费 WebSocket 系统事件；订单扫描仅用于漏消息后的补偿。
  补偿和历史任务恢复必须重新核对订单归属、状态及自动发货开关。
  已取消、已完成或已发货订单不得继续执行旧自动交付任务。
- 平台阶段必须显式建模。支持闲鱼小刀时，“待刀成”只能按独立开关执行免拼；
  实时流程必须等最终“待发货”事件才交付。补偿只能依据已持久化的免拼成功或最终阶段事实，
  并重新核验订单状态，不得推断阶段或调用免拼。未支持的交易类型必须拒绝自动处理并提示原因。
- 多规格订单必须按完整规格组合匹配；覆盖全部商品或规格的规则必须显式配置。
- 必须持久化执行状态，以平台、账号、订单及交付动作标识去重。
  并发通知、重连重放和重启不得创建重复业务交付；人工补发必须关联原记录并记录原因。
- 必须区分“确定未发送”“平台已确认接收”“结果未知”，不能把超时等同于失败。
  对外发送前必须持久化内容或可恢复引用及尝试状态，覆盖发送期间崩溃的恢复场景。
  结果未知时保留原内容、停止盲目自动重发并提示人工核对；不得声称网络层严格恰好一次。
- 库存卡密必须原子预留并绑定订单，确定成功后完成扣减；只有确定未发送才可按规则释放。
  结果未知时不得回库、重新分配或获取另一张卡。外部取卡必须保存请求标识与返回内容；
  结果未知且供应商不支持幂等或查询时，必须转人工处理。
- 消息交付与平台确认发货是独立结果。只有所需内容全部确认发送成功后，
  才可按配置确认平台发货；关闭平台确认发货不得隐式关闭文字交付。

理由：虚拟商品通常无法撤回，漏单和重复卡密的代价高于少量执行延迟。

### II. 平台接入与发货业务分离

平台协议、登录、连接维护和发送能力必须封装在独立适配模块中。
共用业务层负责规则、交付、库存、重试决策、人工处理和审计。

- 适配器必须返回结构化事件、订单事实、能力声明和结果分类，不能直接决定规则或扣减库存。
- 共用模型不得以闲鱼 Cookie、消息格式或商品字段代替跨平台身份和状态。
  平台差异通过适配器转换并保留必要来源事实，不得强行等同不同交易阶段。
- HTTP、桌面页面和托盘只负责交互调用，不得包含交易规则、SQL 或平台协议解析。
  核心交付必须能在管理页面关闭后持续运行。
- 数据访问经过明确的仓储接口或事务边界；外部网络调用不得占用数据库事务或库存锁。
- 新平台必须分别验证订单读取、付款识别、买家定位、消息发送和发货确认能力。
  模板、模拟数据或客服回复演示不能标记为完整自动发货支持。
- 淘宝千牛允许独立 Windows 桥接组件，但必须记录权限、进程生命周期、桌面会话依赖和契约。
  不得为了统一语言而掩盖必需的运行环境。

理由：增加淘宝及后续平台时，应复用交付能力，而非复制整个应用。

### III. 轻量部署，以测量决定优化

默认采用模块化单体、本地持久化和一个主要服务进程，优先降低安装、升级和排障成本。

- 技术路线固定为 Rust + TypeScript：Rust 负责后端与核心业务，TypeScript 负责管理界面。
  宪章不预设前端框架、异步运行时、HTTP 框架、数据库、构建工具或桌面外壳。
  具体选型、版本及浏览器接入方案由实施计划按功能需要和轻量原则记录，不凭语言名称承诺性能。
- 首版优先 Windows 本地运行：后端可嵌入前端构建产物，通过本机浏览器管理。
  桌面外壳、托盘、开机启动和安装器仅在对应需求进入规格后引入。
  正式发布的卖家安装流程不得要求 Rust 或 Node.js 编译环境，必须在无开发环境条件下验证。
- 首版不得默认引入 Redis、外部数据库、消息中间件、微服务或必需的云控制面。
  只有具体能力或测量证明必要时，才在计划中说明收益、替代方案和部署成本。
- 浏览器自动化按经验证的平台需要使用，必须定义创建、复用、回收和退出策略。
  不得为减小安装包删除必要验证能力，也不得宣称系统 WebView 可直接替代 Chromium。
- 性能评估必须分别记录服务、浏览器、桌面外壳及整体进程资源，
  注明操作系统、构建版本、账号数、启用功能和测试时长。
  发布基线至少覆盖冷启动、空闲内存、在线内存与 CPU、本地事件处理延迟和平台确认耗时；
  平台网络耗时必须与本地处理耗时分开。
- 优化或替换技术栈必须提供同场景对比；资源预算在首个运行原型测量后写入计划。
  没有运行证据时只能说明目标，不得标注“最轻量”“零掉单”或“全天候稳定”。

理由：浏览器依赖和架构复杂度可能比语言差异更影响实际体验。

### IV. 关键交易行为必须可验证、可追溯

AI 生成和人工编写的代码适用相同标准。通过编译或拥有界面不代表发货可用。

- 修改事件解析、规则、规格数量、库存、重试、并发或状态迁移时，必须更新相应行为测试。
  缺陷修复必须有覆盖原问题的回归用例。
- 关键测试必须覆盖未付款、普通聊天、错误账号、规格缺失、重复事件、并发卡密分配、
  超时、部分成功、中断恢复、取消订单和凭证失效；支持小刀后必须验证其阶段顺序。
- 优先使用脱敏协议夹具、模拟平台、临时数据库和本地浏览器页面。
  测试不得默认消费真实库存或向真实买家发送消息；实账号验证必须单独标识范围与授权。
- 声称平台支持前必须记录实际账号环境下验证的功能、客户端或协议版本、日期和未验证项。
  缺少账号时继续完成确定性测试，但不能把模拟通过表述为实单通过。
- 日志及管理界面必须能按平台、账号、订单、交付任务关联事件，
  显示状态、尝试次数、最后错误和可执行操作；未知结果、库存不足和账号离线必须明确提示。
- 后台任务必须定义所有者、取消、超时、重试上限或退避、退出等待及重启恢复策略。
  不得无限紧密重试、退出后遗留失控任务或让旧请求覆盖新账号状态。
- 前后端契约必须有明确类型与运行时输入校验；破坏性修改同步调用方、测试和迁移说明。
  前端经功能 API 适配层访问服务，必须处理取消、重复提交和过期响应。

理由：可靠性来自可重复的行为证据和故障恢复，而非代码量或生成速度。

### V. 本地数据边界与参考源码隔离

账号凭证、买家信息和未使用卡密属于敏感数据，默认保存在用户控制的本地环境。

- 管理服务默认绑定回环地址，并具有初始化认证与访问控制。
  外网访问必须作为显式部署模式设计，不能默认监听所有网卡。
- 凭证持久化必须使用加密或操作系统安全存储，明确密钥来源与备份恢复方式。
  列表、状态、日志、错误及通知不得包含明文 Cookie、Token、密码或完整卡密。
  展示交付内容必须经过授权，不得默认进入通用查询或前端持久化状态。
- 不默认上传凭证、订单、聊天和库存，不为发货强制接入 AI 服务。
  供应商 API 或第三方通知必须明确发送字段、凭证用途及超时行为。
- 数据结构变更必须有版本化迁移和验证；业务数据升级必须说明备份与恢复方法。
  不得通过删库或清空任务状态解决正常升级问题。
- 仓库根目录是轻交付的新项目；`Ydisks-Xianyu-Helper/` 仅作本地参考，
  必须排除在 Git 跟踪、发布打包和上传清单之外，不能成为运行时、构建或测试依赖。
- 上游历史治理文件和已撤销 AGENTS 规则不得自动成为本项目约束。
  参考时记录上游地址与提交；复制或移植实质代码、页面和测试夹具时，
  必须核对许可并保留适用的版权、LICENSE、NOTICE 和修改说明。
  忽略参考目录不免除复用代码的许可义务。
- 实际凭证、运行数据库、日志、构建缓存和机器私有配置不得提交。
  发布前必须检查暂存内容及产物清单；Git 忽略规则不等于打包排除规则。

理由：参考项目应降低探索成本，同时保持轻交付独立构建、分发和维护。

## 产品范围与技术约束

产品名称为“轻交付”，仓库标识 `qing-delivery`，定位为多平台虚拟商品自动发货助手。
初期服务卖家自用和少量店铺，保留多账号标识，不默认建设公共 SaaS、多租户计费或插件市场。

- 首个可验收版本聚焦闲鱼：账号接入与状态、商品到固定文本的映射、
  付款后发送链接和提取码、发货记录、异常提示及受控人工补发。
  未纳入范围的规格或订单类型必须在界面及执行层明确限制。
- 淘宝千牛是后续明确目标，先验证订单与发送通道，再承诺完整接入。
  拼多多、抖店等按实际需要逐个立项，空实现不能充当支持。
- 固定文本、本地卡密及外部取卡是可扩展内容来源；首版实现固定文本即可。
  后两者在对应规格定义库存、供应商幂等和补发语义后实现。
- AI 客服、自动议价、商品发布、擦亮、评价和营销不属于首版必需能力。
  增加这些功能不得改变已付款才交付、未知结果停止重放等交易原则。
- 参考 Go 项目的流程与协议，Rust 后端视为新实现并重新验证。
  上游界面可按许可、契约及实施计划的技术选型复用，不要求逐行翻译或完整搬运上游功能。
- 首版持久化方案由实施计划确定，必须满足本地运行、事务一致性和中断恢复要求，
  不预设数据库产品，不承诺兼容上游数据结构或同时支持多种数据库。
  导入上游数据必须单独定义字段映射、敏感数据处理和回滚方案。
- 目录结构由首个实施计划确定，区分界面、业务、平台适配和持久化职责；
  不为目录数量、框架统一或语言比例增加服务。

## 开发流程与交付门禁

每个功能先定义用户场景、边界、非目标和验收，再制定方案、拆分可验证任务并实施。
宪章本身不自动授权后续开发、账号操作或发布。

计划中的 Constitution Check 必须逐项检查：

1. 是否符合当前范围，未支持平台与交易类型是否明确拒绝。
2. 是否有可信付款依据、完整身份关联、持久化去重和未知结果处理。
3. 是否保持平台与业务分离，新增部署依赖是否有必要性证据。
4. 是否定义关键测试、实账号验证边界、日志与人工处理路径。
5. 是否保护敏感数据，避免依赖或打包上游参考目录。
6. 是否明确性能测量条件、升级影响和业务数据兼容策略。

Rust 改动至少通过格式检查、Clippy 和相关测试；前端改动至少通过类型检查、行为测试和构建。
具体命令及版本写入实施计划；集成后增加可重复的启动、健康检查和正常退出验证。
纯文档修改仅执行相关文档校验，不启动服务或执行无关平台操作。

交付必须列出改动、验证命令及结果、未验证行为与已知限制。
不得删减关键断言来通过检查，不得将未验证能力标记为完成。
不继承上游固定覆盖率、逐变量注释或六阶段提交制度；注释必须准确解释业务约束、
并发所有权与不明显的取舍，测试必须验证行为而非复述实现。

构建产物必须脱离参考目录运行。发布前核对运行环境、许可声明、数据目录、浏览器依赖和版本；
构建完成不等于已获准上传或部署。

## Governance

本宪章是轻交付的项目设计与开发依据，替代未实例化模板，不继承参考项目治理计划。
执行时遵循适用指令层级和用户最新明确决定；用户变更项目原则后，同步本文与受影响规格。

- 修订必须说明原因、影响原则、兼容性和必要迁移，并更新顶部 Sync Impact Report。
  技术栈整体切换或取消交易可靠性原则属于重大治理变更，不得作为普通重构静默发生。
- 版本采用语义化规则：不兼容的原则删除或重定义递增 MAJOR；
  新增原则或实质扩展约束递增 MINOR；不改变含义的澄清和文字修正递增 PATCH。
- Ratified 保留首次制定日期，每次实质修改更新 Last Amended。
  首次制定采用 1.0.0，日期为 2026-09-22。
- 每个计划和交付审查必须核对宪章。偏离必须记录条款、必要性、替代方案、影响及纠正条件，
  不得改写测试或隐藏范围来规避原则。
- 平台权限、实账号兼容性、资源预算和依赖版本由对应计划提供证据。
  未验证不是默认成功，也不要求停止其他独立工作。
